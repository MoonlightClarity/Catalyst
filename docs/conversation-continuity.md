# Chat conversation continuity and crash recovery

Status: optional development workflow. This is not part of Catalyst runtime behavior.

## Purpose

Long ChatGPT development conversations can become slow, unstable, difficult to navigate, or unusable after a crash. The continuity workflow lets a fresh conversation recover exact context from an older ChatGPT thread instead of relying only on memory summaries or manually copied excerpts.

The workflow combines three optional development tools:

- **Opera Browser Connector** reads and navigates ChatGPT conversations.
- **Catalyst Chat Bridge** can draft or send a message in a ChatGPT conversation opened in Opera.
- **Remote Desktop Commander** maintains the local Catalyst workspace and can generate bridge commands.

## Recovery model

A new ChatGPT conversation does **not** become the old conversation. Instead, the new conversation treats older threads as readable/queryable context sources:

```text
fresh recovery chat
      |
      | Opera: navigate/read
      v
older ChatGPT thread
      ^
      | Catalyst Chat Bridge: optional targeted query
      |
Remote Desktop Commander / local bridge command
```

The old thread remains the source of record for its own discussion. The fresh thread becomes the active working conversation.

## When to use it

Use this workflow when a long thread is visibly degrading, repeatedly crashes, stops loading reliably, or has become too large to continue safely. It can also be used proactively before a major context rollover.

## Standard crash-recovery procedure

1. Start a fresh ChatGPT conversation and identify it as the continuation/recovery thread.
2. Keep Opera logged into the same ChatGPT account and ensure Browser Connector is connected.
3. Open the old conversation in Opera. Prefer its stable `https://chatgpt.com/c/...` URL rather than relying on a sidebar title.
4. Use Opera Browser Connector to read the old conversation directly. Recover exact decisions, commands, errors, file names, and unresolved work before asking the user to repeat them.
5. If the needed detail is not obvious from reading, use the Catalyst Chat Bridge to ask the old thread a narrow question. Example: `Summarize the last validated Catalyst checkpoint, unresolved defects, and exact next action.`
6. Read the old thread's reply through Opera and bring the relevant facts into the fresh conversation.
7. Continue implementation from the fresh conversation. Do not keep extending the failing thread simply because it can still accept one more message.

Prefer **read-only retrieval first**. Sending a query changes the old conversation and should be used only when direct inspection is insufficient or a compact handoff from that thread materially improves recovery.

## Proactive rollover procedure

When a conversation is still healthy but is becoming very long, recover before failure:

1. Finish the current coherent code/test checkpoint.
2. Record the local source state and validation result in Catalyst documentation.
3. Start a fresh ChatGPT conversation.
4. Use Opera to inspect the old thread's final section and verify the handoff against the actual local files.
5. Ask the old thread for a compact checkpoint only if needed; do not treat that summary as more authoritative than the source tree, tests, or exact old messages.
6. Continue in the fresh thread with the old thread available as a context archive.

This reduces context degradation without requiring a single indefinitely growing conversation.

## Recovery priority

When sources disagree, prefer them in this order:

1. current local Catalyst files and test/build output;
2. exact messages retrieved from the relevant older chat;
3. project documentation/checkpoint files;
4. a handoff summary generated by the older chat;
5. retained conversational memory.

A summary is a compression aid, not the source of truth.

## Catalyst Chat Bridge safety and behavior

The bridge is development-only and runs as an unpacked Chromium/Opera extension scoped to `chatgpt.com`. It does not belong in Catalyst's product runtime or dependency graph.

Bridge commands support two modes:

- `draft` inserts text into the ChatGPT composer without submitting it;
- `send` inserts text and activates the ChatGPT Send control.

Use `draft` when validating a new browser/editor state or after changing bridge code. Use `send` only after draft insertion has been verified.

The bridge command contains a local secret token. Do not publish the token, commit it to a public repository, paste it into documentation, or expose bridge-command URLs outside the local development environment.

If a full navigation reports `composer not found`, allow the ChatGPT page to finish loading and resend the command against the already-loaded conversation. A hash-only retry has been validated successfully. Reload the unpacked extension from `opera://extensions/` after changing its source files.

## Known limits

- The bridge depends on ChatGPT's browser editor/Send controls and may need maintenance after UI changes.
- Browser navigation and message submission do not transfer this chat's hidden context into another chat; only the text actually sent is transferred.
- Older chats can themselves contain stale assumptions. Verify recovered claims against the working tree and current tests.
- This workflow mitigates conversation-length/context degradation; it does not eliminate the need for project documentation and reproducible checkpoints.

## Observed maximum-length behavior

The ChatGPT banner **“This conversation has reached the maximum allotted length”** should not be interpreted as proof that the thread can no longer send or receive messages. In observed Catalyst development use, a thread displaying that warning could still accept new messages and return responses, but at **severely degraded performance**.

Operationally, the wording is misleading because it reads like a hard stop while the observed behavior is closer to a degraded/unsupported state. The ability to send one more message is therefore **not evidence that the conversation remains healthy**.

Treat this banner as an immediate rollover trigger: finish only the minimum recovery/handoff action needed, move active work to a fresh conversation, and use the old thread through Opera/Chat Bridge as an archive or targeted context source. Do not keep extending it merely because message submission still technically works.

## Access escalation during recovery

The assistant is explicitly permitted to ask for additional access at any time when broader access would materially improve conversation recovery, context retrieval, browser automation, local validation, or continuity of development work.

This permission is a standing invitation to request access, not automatic authorization to expand privileges. Any new connector, browser capability, filesystem scope, account connection, extension permission, or other access expansion still requires the user's explicit approval at the time it is requested. Prefer the narrowest access that solves the problem, and explain what additional access would enable before asking.

## Bridge stability requirement for rollover

Before using the bridge for a proactive rollover, prefer the hardened build (`0.2.0` or later). It retains a command across slow full-page startup until the ChatGPT composer is actually available, waits up to 45 seconds, and suppresses duplicate handling while a command is in flight. This reduces the risk that a rollover handoff is silently lost during navigation.

This profile check is part of crash recovery and proactive rollover. It prevents a fresh chat from stopping, reusing, or contaminating another chat's GUI workspace. If profile metadata and an old chat disagree, prefer the current local profile/state files.
